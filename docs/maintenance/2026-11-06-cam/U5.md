### U5-01 — Dense-model load_balance/specialization score 0.5 with weight applied, contradicting "excluded entirely"
`src/model_headroom/analysis/orchestrator.py:465-501`
`src/model_headroom/analysis/scoring.py:42-47,122-130`

severity: S-INVARIANT | code: S-INVARIANT

evidence:
```
if resolved_architecture == "dense":
    signals.append(
        _run_signal("load_balance", analyze_load_balance,
            ExpertActivationData(metadata={"num_experts": 1, "num_experts_architectural": 1}, layers={})))
```
```
if signal.status == "single_expert": return 0.5   # scoring.py:44
...
if signal.status == "not_applicable": continue     # scoring.py:123 — single_expert NOT skipped
```

mechanism: Orchestrator injects `num_experts=1, num_experts_architectural=1` for dense models, so `analyze_load_balance` returns `signal_status="single_expert"`, `balance_ratio=None`. `scoring.py:_score_signal` maps `single_expert` → 0.5 (not excluded). `compute_headroom_score` only skips `not_applicable` (line 123), so `single_expert` signals keep their weight (0.10 each) and contribute 0.5·w to the composite. Same path for `specialization` (line 494-501). AGENTS.md:96 and headroom-signals.md:193-200 state not_applicable signals are "excluded from numerator and denominator" — but dense models never get `not_applicable`; they get `single_expert`, which IS scored.

why-not-intended: Contract says dense models mark load_balance/specialization `not_applicable` and exclude them. The code instead marks them `single_expert` and scores them at neutral 0.5 with full weight. The composite includes 0.20 weight (0.10+0.10) at neutral value, diluting the 5 universal signals rather than renormalizing over them.

test_protocol_gap: No test asserts dense-model composite excludes load_balance/specialization weight.

suggested fix: Orchestrator should mark dense-model load_balance/specialization as `not_applicable` (status string "not_applicable", data=None) so `compute_headroom_score` skips them entirely; or `_score_signal` should treat `single_expert` as excludable rather than scoring 0.5.

### U5-02 — dead_neurons NaN propagation masks dead neurons as score 1.0
`src/model_headroom/signals/dead_neurons.py:21-26,32-39`

severity: G-EDGE | code: G-EDGE

evidence:
```
dead_mask = neuron_means < threshold   # NaN < 1e-6 is False → NaN neuron not counted dead
flat = tensor.float()
activation_rms = float(torch.sqrt((flat**2).mean()).item())   # NaN if any NaN present
```

mechanism: If the activations tensor contains NaN, `neuron_means < threshold` yields False for NaN means (NaN comparisons are false), so NaN-containing neurons are never counted as dead. `dead_fraction` undercounts dead neurons. `activation_rms`, `mean_abs`, `variance` all become NaN (torch ops propagate NaN). `DeadNeuronReport` carries NaN fields; orchestrator wraps it as `status="computed"`; `_score_signal` returns `1.0 - dead_fraction` — if dead_fraction is NaN, the score is NaN, and `compute_headroom_score` yields NaN composite. NaN is never raised; it flows into the report as a valid-looking score.

why-not-intended: NaN should surface as an error or be guarded, not silently produce a "healthy" score of 1.0 (or NaN composite).

test_protocol_gap: No test feeds NaN activations and asserts status="error" or dead_fraction handling.

suggested guard: Guard against NaN input (e.g. `torch.isnan(tensor).any()`) and return `signal_status="error"` before computing statistics.

### U5-04 — growth_factor math.log(0) on zero model_params/measured_loss silently becomes "error" → score 0.0, conflating invalid input with computation failure
`src/model_headroom/signals/growth_factor.py:128-129`

severity: G-EDGE | code: G-EDGE

evidence:
```
log_params = [math.log(p.model_params) for p in isoflop_points]   # line 128
log_loss = [math.log(p.measured_loss) for p in isoflop_points]    # line 129
...
except Exception as e:   # line 160
    return GrowthFactorReport(..., signal_status="error", ...)
```

mechanism: If any `IsoFLOPPoint.model_params == 0` or `measured_loss == 0`, `math.log(0)` raises `ValueError`, caught by the broad `except Exception` at line 160, returning `signal_status="error"`. Orchestrator wraps as `status="error"`; `_score_signal` maps error → 0.0. Invalid input (zero param count / zero loss) is indistinguishable from a genuine computation failure. Both score 0.0 with full weight (0.20).

why-not-intended: Invalid input should be surfaced as `insufficient_data` or a distinct status, not merged with computational error.

test_protocol_gap: No test feeds `model_params=0` or `measured_loss=0` and asserts a distinct status.

suggested fix: Validate inputs before `math.log`; return `signal_status="insufficient_data"` (or similar) for non-positive values rather than `error`.

### U5-05 — growth_factor alpha is unbounded and can exceed [0,1], but _score_signal clamps to [0,1] silently
`src/model_headroom/signals/growth_factor.py:137-138`
`src/model_headroom/analysis/scoring.py:60-62`

severity: S-INVARIANT | code: S-INVARIANT

evidence:
```
alpha = 2 * a * mean_log_params + b   # growth_factor.py:138 — any real, unbounded
...
return float(min(1.0, max(0.0, r.alpha)))   # scoring.py:62 — silent clamp
```

mechanism: `alpha` is the derivative of a quadratic fit and can be any real number (negative or >1). `_score_signal` silently clamps to [0,1]. A model with alpha=2.5 (strong diminishing returns beyond expectation) scores identically to alpha=1.0. The clamp hides the true value; the report's `alpha` field carries the raw value but the composite discards the distinction.

why-not-intended: The composite should reflect the actual alpha magnitude, not silently clamp. Clamping to [0,1] loses information about extreme regimes.

test_protocol_gap: No test feeds points producing alpha outside [0,1] and asserts clamping behavior.

suggested fix: Document the clamp as intentional saturation, or map alpha to a bounded score via a sigmoid/softclip rather than hard clamp.
