## Findings

### U3-01 — Dense-model MoE signals scored as neutral single_expert instead of excluded not_applicable, diluting the composite score

**file:line** `src/model_headroom/analysis/orchestrator.py:465-492` and `:494-501`; `src/model_headroom/analysis/scoring.py:123-124`
**severity** HIGH — a wrong composite number
**code** S-INVARIANT
**evidence**
```
orchestrator.py:465-475  if resolved_architecture == "dense":
                             _run_signal("load_balance", analyze_load_balance,
                                 ExpertActivationData(metadata={"num_experts": 1, ...}, layers={}))
orchestrator.py:494-501  if resolved_architecture == "dense":
                             _run_signal("specialization", analyze_specialization,
                                 ExpertWeights(expert_weights=[], layer_name="dense"))
scoring.py:123-124         if signal.status == "not_applicable":
                             continue        # excluded from numerator AND denominator
```
**mechanism** For a dense model, `analyze_load_balance` receives `num_experts_architectural == 1` and returns `signal_status="single_expert"` (load_balance.py:77-85); `analyze_specialization` receives `< 2` experts and returns `signal_status="single_expert"` (specialization.py:54-61). `_score_signal` maps `single_expert` → 0.5 (scoring.py:44-45), but `compute_headroom_score` excludes only `not_applicable` (scoring.py:123-124), so both dense MoE-only signals are *included* in the composite with weight 0.10 each at score 0.5. Result: a dense model whose 5 universal signals are all perfect scores 1.0 caps at composite 0.90 instead of 1.00 ((0.80 + 0.10)/1.00 vs 0.80/0.80). The documented contract says dense `load_balance`/`specialization` are `not_applicable` and excluded with weight renormalization over the 5 universal signals.
**why-not-intended** Violates `AGENTS.md:96` ("Dense models mark load_balance/specialification not_applicable; weights renormalize over the remainder") and `docs/model-headroom/README.md:95` ("R-06 and R-07 are marked not_applicable and excluded from the composite score (computed over the 5 universal signals only)"). Code emits `single_expert`; contract requires `not_applicable`.
**test_protocol_gap** n/a — S-INVARIANT, not G-ERR/G-EDGE/G-SEC.
**suggested fix** Emit `signal_status="not_applicable"` for dense-model `load_balance`/`specialization` so `compute_headroom_score` excludes them and renormalizes weights; or remove single_expert weight from the dense composite.

### U3-02 — Orchestrator-wrapped signal exceptions lose their error message in the human report

**file:line** `src/model_headroom/reporting/human_report.py:24-25`; `src/model_headroom/analysis/orchestrator.py:147-155`
**severity** MEDIUM
**code** G-ERR — suppressed/misattributed error information
**evidence**
```
human_report.py:24-25  if signal.status == "error":
                         return f"  {name:<30} [ERROR — {getattr(signal.data, 'error_message', 'unknown') if signal.data else 'no data'}]"
orchestrator.py:147-155  except Exception as e:
                           return SignalResult(signal_name=name, status="error", data=None,
                                               duration_seconds=duration, error_message=str(e))
```
**mechanism** An unexpected signal exception → `_run_signal` catches it → `SignalResult(status="error", data=None, error_message=str(e))`. `human_report.py:24-25` reads `error_message` from `signal.data`; since `signal.data is None`, it displays `[ERROR — no data]`. The actual cause `str(e)` lives in `signal.error_message`, which `human_report` never reads. The operator sees a signal errored with no reason and cannot diagnose it.
**why-not-intended** Error visibility is part of the reporting contract; hiding the failure cause turns an actionable error into an opaque `[ERROR — no data]`. No clause in AGENTS.md or the README sanctions losing exception text.
**test_protocol_gap** Required for G-ERR: no test forces an unexpected signal exception and asserts the human report surfaces `signal.error_message` rather than `no data`; an all-mocked signal suite would not exercise the orchestrator exception → reporter path.
**suggested fix** `human_report` should fall back to `signal.error_message` when `signal.data is None`, e.g. display `signal.error_message or 'no data'`.

### U3-03 — `--gradient-diagnostics` failures are silently swallowed; operator gets no diagnostic output and no warning

**file:line** `src/model_headroom/analysis/orchestrator.py:624-625`
**severity** MEDIUM
**code** G-ERR — suppressed error
**evidence**
```
orchestrator.py:624-625  except Exception:  # noqa: S110
                           pass
```
**mechanism** With `--gradient-diagnostics`, `compute_gradient_diagnostics=True` and the block at orchestrator.py:559-623 imports/computes `gradient_coherence` and `gradient_effective_rank`. Any exception (missing torch, malformed pair shapes, empty batch groups, etc.) is caught by the bare `except Exception: pass`. The `gradient_diagnostics` key is never added to `report_metadata`, no warning is printed, and `cli.py` proceeds to render the report as if diagnostics ran. The operator requested a feature and receives silence they cannot distinguish from "diagnostics not requested."
**why-not-intended** An explicitly requested, opt-in diagnostic failing silently violates the fail-loudly principle; there is no documented contract allowing silent degradation of `--gradient-diagnostics`.
**test_protocol_gap** Required for G-ERR: no test injects a failure inside the gradient-diagnostics block and asserts a warning is emitted or `gradient_diagnostics` reflects the failure rather than silence.
**suggested fix** Replace the bare `pass` with a warning to `stderr` and/or record a `gradient_diagnostics` error note in `report_metadata` so the operator is informed.
