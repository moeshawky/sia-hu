### U1a1-01 — upstream.py lacks defensive error handling; connect/read failures propagate uncaught

**file:line**: upstream.py:132-163 (`_proxy_sync`), upstream.py:165-198 (`_proxy_stream`)
**severity**: LOW
**code**: G-ERR

**evidence** (quoted ≤8 lines):
```
async def _proxy_sync(
    self,
    method: str,
    path: str,
    headers: dict[str, str],
    body: dict[str, Any] | None,
) -> UpstreamResponse:
    """Non-streaming proxy: forward request, return complete response."""
    forwarded = {k: v for k, v in headers.items() if k.lower() != "content-length"}
    start = time.monotonic()
    resp = await self._client.request(
        method=method,
        url=path,
        headers=forwarded,
        content=json.dumps(body).encode() if body else None,
    )
```
`_proxy_stream` (lines 165-198) has the same shape with no try/except around `self._client.send(response, stream=True)`.

**mechanism**: Neither `_proxy_sync` nor `_proxy_stream` wraps the httpx call in try/except. `httpx.ConnectError`, `httpx.ConnectTimeout`, `httpx.ReadTimeout` propagate as uncaught exceptions. App.py callers do catch them — `_handle_completion_request` (lines 970-982), `_handle_embedding_request` (lines 1324-1336), `_handle_models` (lines 673-687) — converting to 502 "upstream unavailable". So current clients see 502 for upstream-down and the upstream's actual HTTP status for upstream-rejected (the distinction is real, but it lives entirely in app.py's except blocks, not in upstream.py's design). upstream.py's docstring declares no `Raises`, yet `proxy()` can raise httpx exceptions. Any future caller that does not wrap `proxy()` gets an unhandled exception → FastAPI 500.

**why-not-intended**: UNKNOWN — could be deliberate (callers own error handling) or an oversight. upstream.py provides no defined error type or status mapping of its own.

**test_protocol_gap**: No unit test covering `_proxy_sync`/`_proxy_stream` with `httpx.ConnectError` → expected 502 mapping; no test asserting the upstream-down vs upstream-rejected distinction.

**suggested fix**: Add structured error handling in upstream.py (map httpx.RequestError subtypes to a defined exception or status), or explicitly document that all callers must wrap `proxy()` in try/except.

### U1a1-02 — ollama embedding translation crashes on non-dict upstream JSON, misattributed as 502

**file:line**: app.py:1057 (`_translate_ollama_response`, `raw.get("embeddings")`), app.py:1256 (call site `upstream_resp.body or {}`)
**severity**: LOW
**code**: G-ERR

**evidence** (quoted ≤8 lines):
```
@app.py:1256:
                openai_response = self._translate_ollama_response(
                    upstream_resp.body or {}, forwarded_model
                )
@app.py:1057:
        ollama_embeddings = raw.get("embeddings", [])
```

**mechanism**: `_proxy_sync` (upstream.py:150-156) wraps non-JSON upstream bodies as `{"raw": resp.text}` (a dict), but if upstream returns *valid non-dict JSON* (a list, string, or number), `response_body` is that non-dict value. At line 1256, `upstream_resp.body or {}` preserves a truthy non-dict (e.g. a list), and line 1057 calls `.get("embeddings")` on it → `AttributeError: 'list' object has no attribute 'get'`. The exception propagates to the `except Exception` at app.py:1324, which returns 502 "upstream unavailable" — a misattribution: this is a proxy response-shape bug, not an upstream failure. Reachable only when ollama `/api/embed` returns non-dict JSON (misconfigured or broken upstream), but the crash is avoidable.

**why-not-intended**: UNKNOWN — defensive coercion was not added.

**test_protocol_gap**: No test feeding a non-dict JSON body through the ollama embedding path; no test asserting graceful degradation vs 502.

**suggested fix**: Coerce `raw` to a dict before `.get()`: `raw if isinstance(raw, dict) else {}`.

### U1a1-03 — `/v1/models` broad `except Exception` misattributes proxy bugs as upstream failure

**file:line**: app.py:673 (`_handle_models` exception handler)
**severity**: MEDIUM
**code**: G-ERR

**evidence** (quoted ≤8 lines):
```
except Exception as e:
    with contextlib.suppress(OSError):
        self._capture_logger.log_error(
            {
                "turn_id": str(uuid.uuid4()),
                "created_at": datetime.now(UTC).isoformat(),
                "error_body": str(e),
                "request_type": "models",
                "error_category": "connection_error",
            }
        )
    return JSONResponse(
        status_code=502,
        content={"error": "upstream unavailable"},
    )
```

**mechanism**: The `except Exception` at line 673 catches *every* exception in the `/v1/models` handler — including proxy-side bugs in `sanitize_models_list`, `json.dumps(sanitized)`, or attribute errors — and returns 502 "upstream unavailable" with `error_category: "connection_error"`. The client cannot distinguish upstream-down from a proxy-side defect; the error row in `errors/` is tagged `connection_error` regardless of the true cause.

**why-not-intended**: UNKNOWN — over-broad exception handling.

**test_protocol_gap**: No test injecting a `sanitize_models_list` failure (e.g., non-dict upstream body) and asserting a 500 or distinct error category rather than 502 "upstream unavailable".

**suggested fix**: Narrow the except to connection errors (httpx.RequestError) only; let programming errors propagate or return 500 with a distinct category.
