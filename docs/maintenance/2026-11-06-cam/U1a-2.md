### U1a2-01 — Rerank ollama 501 returned but never captured or logged (S-WIRE, LOW)

file:line: src/capture_proxy/app.py:1422-1426

evidence:
```
1421:         # Ollama does not support rerank
1422:         if self._backend == "ollama":
1423:             return JSONResponse(
1424:                 status_code=501,
1425:                 content={"error": "rerank is not supported for ollama backend"},
1426:             )
```

mechanism: The ollama branch at 1422-1426 returns 501 before the CaptureRecord is built (1447-1471) and before any `_log_capture`/`log_error` call. The record constructed at 1447 never exists for this path, so nothing is written to raw/ or errors/. Contrast the 502 upstream-failure path at 1499-1508, which sets upstream_status/error_body and calls `self._log_capture(record)`. Validation 422s at 1377-1392 log via log_error (OSError suppressed). Classification (1510-1673) and image (1675-1834) have no ollama branch at all — they forward to upstream and log whatever status comes back. AGENTS.md documents "Ollama returns 501" by design (not a gap per se), but the *recording* is inconsistent: the proxy-generated 501 is the only synthetic negative response in this range that lands nowhere.

why-not-intended: UNKNOWN - candidate only. The early return is deliberate, but no requirement was read stating 501 must be excluded from capture; consistency with the 502 path argues it should be recorded.

test_protocol_gap: No test asserts an ollama-rerank 501 appears in errors/ (or deliberately excludes it).

suggested fix: Route the ollama 501 through `log_error` like the validation-error path, or document the exclusion in the handler invariant block.

### U1a2-02 — `_refresh_runtime_on_upstream_failure` spawns unbounded concurrent refresh work, no lock or dedup (G-EDGE, MEDIUM)

file:line: src/capture_proxy/app.py:2572-2593

evidence:
```
2572:     async def _refresh_runtime_on_upstream_failure(self, record: CaptureRecord) -> None:
2586:         refresh_snapshot = await asyncio.to_thread(
2587:             RuntimeSnapshot.get,
...
2590:             force=True,
2591:         )
2592:         record.run_id = refresh_snapshot.run_id
2593:         record.runtime_settings = refresh_snapshot.settings
```

mechanism: Every upstream failure (502 pre-flight at 2101, streaming-failure finally at 2344, connect exceptions) calls this, which runs `RuntimeSnapshot.get(force=True)` off the event loop via `asyncio.to_thread`. Docstring line 2577: "The rebuild runs off the event loop (blocking advisory subprocesses)." There is no lock, no in-flight dedup, no rate limit, and no cap. Under a sustained 502 storm, concurrent requests each spawn their own blocking refresh thread — unbounded thread growth. Records are distinct, so no cross-record corruption, but the process can be flooded with redundant rebuilds.

why-not-intended: UNKNOWN - candidate only. Nothing read states refresh storms are bounded elsewhere.

test_protocol_gap: No concurrency/refresh-storm test; failure tests appear single-shot.

suggested fix: Add an in-flight lock or rate-limit/de-duplicate concurrent forced refreshes.

### U1a2-03 — `_normalize_usage` turns missing/null upstream usage into silent zeros, corrupting context_total aggregates (G-EDGE, MEDIUM)

file:line: src/capture_proxy/app.py:2722-2740

evidence:
```
2729:     prompt_total = usage.get("prompt_tokens") or 0
2733:     completion = usage.get("completion_tokens") or 0
2739:         context_total=prompt_total + completion,
```

mechanism: `usage.get("prompt_tokens") or 0` collapses absent key, explicit null, and real 0 into 0; same for completion_tokens. `prompt_tokens_details or {}` likewise collapses null/missing details, and `prompt_uncached = max(0, prompt_total - prompt_cached)` (2732) hides a cached>total anomaly. Callers gate on `if usage:` (2338), so a non-dict truthy `usage` raises AttributeError inside the streaming `finally` (2338-2341) and propagates out of the generator. AGENTS.md 7b directs operators to compute tokens/min from `usage_normalized.context_total` over JSONL — missing usage silently contributes 0 with no error signal, indistinguishable from a genuine zero-token turn.

why-not-intended: UNKNOWN - candidate only. `or 0` fallback reads as deliberate leniency, but no documented contract says missing usage must normalize to zero rather than absent.

test_protocol_gap: No test feeds upstream usage missing `prompt_tokens`/`completion_tokens`, null `prompt_tokens_details`, or non-dict usage; zero counts are never distinguished from missing.

suggested fix: Preserve absence (optional null fields) or record a usage_present flag so aggregates can exclude missing counts.

### U1a2-04 — Streaming stored body silently drops malformed SSE chunks and concatenates duplicates, diverging from what was forwarded (G-EDGE, LOW)

file:line: src/capture_proxy/app.py:2231-2236, 2254-2256, 2641-2642

evidence:
```
2231:                             if event.get("json_valid") and not event.get("done"):
2232:                                 with contextlib.suppress(
2233:                                     json.JSONDecodeError, TypeError
2234:                                 ):
2235:                                     parsed = json.loads(event["raw_data"])
2236:                                     collected_chunks.append(parsed)
...
2641:                 if delta.get("content"):
2642:                     msg["content"] += delta["content"]
```

mechanism: `collected_chunks` (2076) feeds `_reconstruct_response` (2324-2332) which becomes `record.response` (2332). Malformed/invalid JSON events are dropped by `contextlib.suppress(json.JSONDecodeError, TypeError)` at 2232-2234 (non-alias path) and 2255-2256 (alias path) — no counter, no flag, no record of the drop. `[DONE]` events are correctly excluded (`not event.get("done")` at 2231/2278). Duplicated delta chunks are concatenated verbatim via `+=` at 2641-2642 with no dedup by chunk identity. The client forward is lossless (raw bytes yielded at 2216, sanitized reframes at 2258), but the *stored reconstructed body* can omit malformed events or double-count duplicates, so the capture record no longer matches the bytes the client received.

why-not-intended: UNKNOWN - candidate only. Docstring line 1997 calls the pattern "lossless tee"; losslessness applies to the forward, not necessarily the reconstruction, but the divergence is undocumented.

test_protocol_gap: No test injects malformed SSE chunks or duplicated chunks; `StreamDiagnostics` has no malformed_chunks counter to assert against.

suggested fix: Add a malformed-chunk counter to stream diagnostics, or reconstruct from raw bytes instead of parsed chunks.
