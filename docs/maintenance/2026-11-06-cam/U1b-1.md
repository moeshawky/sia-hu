## Findings

### U1b1-01 — Truncated stream stored as response_body with no in-body completeness marker
File:line: `src/capture_proxy/app.py:2323-2332` (`record.response` set from `collected_chunks` regardless of `done_seen`/`client_disconnected`); `src/capture_proxy/stream.py:431-455` (terminal record carries `classification`/`done_seen`/`client_disconnected`); `src/capture_proxy/models.py:61-68` (`StreamDiagnostics.done_seen`/`client_disconnected` only).
Severity: REQUIRED
Code: G-EDGE — `response_body` may contain a client-disconnected prefix indistinguishable from a complete answer.
Evidence:
```
2323:                 if collected_chunks:
2324:                     reconstructed = _reconstruct_response(
2325:                         collected_chunks, response_object
2326:                     )
2332:                     record.response = sanitized_final
```
Mechanism: client disconnect mid-stream sets `client_disconnected` (app.py:2305-2308) and re-raises; the `finally` block still writes `record.response` from whatever chunks were collected (2323-2332) with no partial flag inside the body; completeness is signaled only outside `response_body` via `terminal.classification` / `StreamDiagnostics.done_seen` / `client_disconnected`. A consumer reading only `response_body`: YES, can mistake a prefix for a complete answer.
Why-not-intended: the honesty flag lives in the sidecar (stream.jsonl terminal), so `CaptureRecord.response` as "the response" for an incomplete stream is a contract gap rather than silent data loss.
Test protocol gap: G-EDGE — no test cited that a consumer can distinguish prefix vs complete from `response_body` alone.
Suggested fix: add a `stream_truncated`/`done_seen` flag to `CaptureRecord`, or document that `response_body` must be read together with `stream_diagnostics.done_seen`.

### U1b1-02 — Comment/heartbeat SSE lines silently dropped from the stored stream body
File:line: `src/capture_proxy/stream.py:77-83`.
Severity: SUGGESTION
Evidence:
```
77:             if not line:
78:                 continue
```
A `: comment` line matches neither `"[DONE]"` (79) nor `startswith("data:")` (81) → no event appended, loop continues; nothing written to stream.jsonl and nothing enters `collected_chunks` (app.py:2231-2236).
Mechanism: heartbeat/comment lines are elided at parse time; downstream cannot detect their presence from the capture.
Why-not-intended: UNKNOWN - candidate only (heartbeat elision may be deliberate; no client-observable breakage named, per failure-prevention rule b).
Test protocol gap: none (behavior, not an error path).
Suggested fix: document the elision in the `stream.py` module docstring, or emit comment lines as a distinct event type if operator visibility is required.

### U1b1-03 — `usage_normalized.context_total` unclamped; can exceed the model's real context
File:line: `src/capture_proxy/models.py:47-51` (plain `int`, default 0, no validator); `src/capture_proxy/app.py:2729-2739` (`context_total = prompt_total + completion`; `prompt_cached` excluded via `prompt_uncached` derivation at 2732).
Severity: SUGGESTION
Evidence:
```
2729:     prompt_total = usage.get("prompt_tokens") or 0
2731:     prompt_cached = details.get("cached_tokens") or 0
2732:     prompt_uncached = max(0, prompt_total - prompt_cached)
2739:         context_total=prompt_total + completion,
```
Mechanism: `context_total` is computed (not copied) from upstream usage; `prompt_cached` is never added to the sum, so no cached-token double-count; nothing clamps `context_total` to the model's real context, and upstream over-reporting of `prompt_tokens` flows straight through. Field is diagnostic-only (models.py:44-45: never substituted into the live response).
Why-not-intended: UNKNOWN - candidate only (diagnostic-only field; may be acceptable as-is).
Test protocol gap: none.
Suggested fix: clamp `context_total` to a configured max, or document it as an unvalidated upstream echo.
